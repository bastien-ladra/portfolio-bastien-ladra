01 · System model

Security follows the artifact.

The project separates controls by lifecycle stage so a reviewer can trace what protects source, dependencies, containers, infrastructure, publication and runtime behavior. The API stays deliberately small; the delivery system is the engineering subject.

03 · Control evidence

Seven workflows, distinct responsibilities.

Instead of one oversized CI file, the repository uses specialized workflows. This keeps responsibilities inspectable and allows security checks to fail independently.

CI

Python tests, Gitleaks secret scanning and stale-lock detection. Dependencies are installed with cryptographic hashes.

CodeQL

Static analysis is separated from functional CI so application-code findings have their own security signal.

Dependencies

Dependency review evaluates changes introduced by pull requests before merge.

Containers

Trivy blocks high/critical OS or library vulnerabilities with known fixes, then emits a CycloneDX SBOM artifact.

DAST

The API is built and started locally in CI, health-checked, then scanned with a digest-pinned OWASP ZAP image and an explicit rules file.

IaC

Terraform format, initialization, validation and tests run alongside a blocking Trivy configuration scan.

Publish

The image is pushed to GHCR by commit SHA, then receives signed provenance and an SBOM attestation tied to its digest.

Small blast radius by default.

The Terraform target is intentionally narrow: Artifact Registry plus an authenticated Cloud Run service with a dedicated runtime identity, deletion protection, bounded scaling and explicit CPU/memory limits.

05 · Validation method

Prefer gates that can prove they fail.

The engineering principle behind the project is falsifiability: a security control is more useful when its blocking behavior can be exercised, observed and explained.

Lockfile drift

CI regenerates runtime and development locks from the declared inputs and compares them with the repository. Any difference becomes a blocking error rather than silent dependency drift.

Terraform policy

Terraform tests and Trivy config scanning turn unsafe infrastructure changes into pull-request failures before any cloud deployment is attempted.

Container vulnerability gate

The built image itself — not only source dependencies — is scanned. HIGH/CRITICAL fixed vulnerabilities return a non-zero exit code.

Runtime DAST

ZAP runs against a real containerized instance after a health check, which tests HTTP behavior that static source analysis cannot observe.

06 · Trade-offs & gaps

What this project does not claim.

A credible security case study should show its boundaries. The repository is a reference implementation, not a production platform, and several controls remain intentionally outside the current scope.

Authentication is infrastructure-level

The current API has no business authentication or authorization model. Cloud Run IAM prevents anonymous service invocation in the Terraform target, but application identity is not modeled.

No runtime detection stack

Health probes are availability controls, not security monitoring. Structured audit logs, alerting, runtime detection and incident-response telemetry remain future work.

DAST is baseline, not exhaustive

ZAP baseline is useful regression coverage but does not replace authenticated active scanning, manual testing or a targeted application security assessment.

Design choice: the project favors a small number of explainable, blocking controls over a large scanner collection. New tools should be added only when they cover a distinct failure mode and produce actionable signal.
