CyberSOC-AI-Lab

An experimental SOC lab built around one constraint: AI may assist analysis, but it must not become the source of truth or make a security decision on its own.

01 · Question

How can AI help without owning the decision?

The project does not attempt to prove that an LLM can replace a SOC analyst. It explores a more constrained workflow: explainable rules detect signals first, evidence remains visible, and local AI assistance may structure the analysis before a human validates the result.

Detection before generation

SSH brute force, web reconnaissance and prompt-injection scenarios are identified by deterministic rules. The model is not asked to discover the original event by itself.

Untrusted evidence

Logs, HTTP parameters, user agents, usernames and model outputs are treated as untrusted data. Their content never becomes trusted instruction material.

Human authority

The model can summarize, propose hypotheses and suggest verification steps. It does not block IPs, modify accounts or execute remediation.

02 · Workflow

The chain keeps evidence visible.

Each stage is intentionally observable so a reviewer can separate detection, evidence creation, AI generation, response evaluation and the analyst's final decision.

04 · Engineering evidence

The lab is also treated as software that needs protection.

The project's credibility does not depend on its AI theme alone. Its development path provides reproducible evidence around code quality, dependencies and the container runtime.

Python quality

Black, Ruff, mypy, Bandit and pytest run in CI with a 90% coverage threshold.

Secrets

Gitleaks scans full Git history. Public demonstration data stays synthetic and uses documentation-reserved address ranges.

Dependencies

Runtime and development dependencies are separated, lockfiles include hashes, CI blocks lock drift and pip-audit checks runtime dependencies.

Container

Digest-pinned Python base, non-root runtime, real healthcheck, blocking Trivy HIGH/CRITICAL fixed-vulnerability scan and CycloneDX SBOM.

Governance

The public repository has an active main ruleset requiring pull requests, up-to-date branches, resolved conversations and the three security/quality checks, with no bypass.

05 · Limits

What this project does not claim.

The experimental boundary is part of the evidence. Visible limitations are more useful than self-assigned maturity scores.

Not a production SOC

No real SIEM/EDR integration, no multi-user authentication, no production database, no large-scale advanced correlation and no automated remediation.

Primarily synthetic data

Versioned scenarios support demonstration and tests. The bounded CIC-IDS2017 work does not amount to representative validation on operational traffic.

No universal AI-security claim

Prompt-injection detection covers controlled patterns. It does not prove resistance to every attack or every model behavior.

No external analyst validation

The human-in-the-loop workflow is implemented, but the project has not yet been evaluated by an external SOC analyst population or on a production event stream.

The next meaningful research step is not more UI. It is a bounded, reproducible public micro-evaluation with a defined dataset slice, pre-registered metrics and explicit error analysis.

06 · Research bridge

A first public AI/cyber proof point, not a conclusion.

CyberSOC-AI-Lab complements my DevSecOps work by moving the trust question into a system that consumes potentially hostile security data itself. It creates a concrete path toward provenance, evaluation, human oversight and secure AI pipelines without overstating the current scope.
